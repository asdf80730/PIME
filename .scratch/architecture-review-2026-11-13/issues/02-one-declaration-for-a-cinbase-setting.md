## Problem

A setting lives in four places plus the eight shipped defaults, and the settings
script restates the Python defaults, so the two copies drift. The drift is
caught only by a 215-line cross-file consistency test, which exists because
there is no single declaration to read.

## Solution

`CinBaseConfig` owns one record list — key, default, control kind, and whether
the value affects the table. The shipped JSONs, the settings-page control and
the `checkConfigChange` reload diff all derive from that list.

## Verification

record list and must stay green; `bash tests/run_local_tests.sh python` green.
Add one new key end-to-end and show that only the record list changed.

Layer-1 membership rule (one place): a row without overrides ships the shared
default to every Service; a row with overrides ships only to the Services it
names, every other Service keeping the identical value through the `__init__`
seed that the same list feeds. `checkConfigChange` diffs exactly the six
**T** rows, in list order.

### One-new-key end-to-end demo

`keyboardLayout` was the orphan: present in the shipped JSONs, absent from
`__init__`. Added as row 55 alone, and (with rows 56-57, the other two
JSON-only orphans `colorCandWnd`/`directCommitString`) one row per key brought
along every projection with no other edit: `__init__` seeds it, the nine
regenerated JSONs carry it, the page radio (`name="keyboardLayout"`) is built
by the script, and it is absent from the table-affecting diff set. Pinned by
`test_one_new_record_propagates_everywhere`; the eight-file trap is now one
row per setting.
