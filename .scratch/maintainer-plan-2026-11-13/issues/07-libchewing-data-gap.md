# Close the two missing libchewing data files

Status: resolved
Category: bug

Summary: `python/libchewing/data/` lacks the two names the 0.12.0 loader asks for
by name, and both log lines are expected rather than a failed load.

Generated by omp (Qwen3.8-Flash-Next) without human creative authorship.

## Problem

The shipped set carries `tsi.dat` and `word.dat`; the pinned loader (0.12.0,
`libchewing/` @ `05ae6bcb`) also asks for `chewing.dat` and `chewing-deleted.dat`.
With those absent, three of #928's fifteen tone-menu cases report the hash-data
character instead of the system-dictionary one, and the loader logs
`Dictionary file not found: chewing.dat` on every start.

## Answer

Measured on this tree, 2026-11-13:

- `git -C libchewing status` → `HEAD detached at v0.12.0` /
  `nothing to commit, working tree clean`, and `git submodule status` lists the
  nested pins, so the submodule is initialized.
- `ls python/libchewing/data/` → `swkb.dat symbols.dat tsi.dat word.dat`, the
  four committed names; `chewing.dat` and `chewing-deleted.dat` are the two absent.
- `python/python3/python.exe -m unittest discover -s tests -p
  "test_chewing_tone_menu.py"` → `Ran 15 tests in 2.927s` / `OK`, so all fifteen
  tone-menu cases answer from the hash pair that *is* shipped and none of the
  three mismatches reproduces at this base.

`docs/agents/chewing-api.md` settles why: the two absent names are the third and
fourth entries of `DEFAULT_DICT_NAMES` in `capi/src/io.rs`, and the
`Dictionary file not found: chewing.dat` line from `src/dictionary/loader.rs` is
the expected trace of a context newing up — `word.dat` plus `tsi.dat` carry the
system dictionary, so the load itself succeeds. Regenerating them, when a release
wants them, is the library's own tool run from `libchewing/data/dict/chewing`:
`chewing-cli init --csv word.csv <out>/word.dat` and the same for `tsi.csv`.
`swkb.dat` and `symbols.dat` are copied verbatim from the submodule's `misc/` and
are also stat'd by `python/input_methods/chewing/chewing_config.py` for its
reload version, which is why the pair stays in the payload.

No file changed: the four committed names are the payload, the two log lines are
the settled expectation, and the fifteen-case suite is the check.
