專案導覽

PIME：把輸入法邏輯搬到行程外

一個 Windows 文字服務 DLL，只負責把按鍵轉發給常駐的啟動器，再由啟動器交給 Python、Node 或 Go 寫的後端。改輸入法不必碰 C++，也不必重新註冊 DLL。

整理自 README.md、HACKING.txt、GLOSSARY.md、docs/research/ 上游比對點 EasyIME/PIME@1458cea 2026-10-20

01概觀

先建立一個心智模型：Windows 載入什麼、什麼東西常駐、什麼東西可以換。

Windows 的 TSF（Text Services Framework）要求輸入法以 in-process DLL 的形式被載入每一個使用它的應用程式。這件事決定了整個設計：C++ 的部分必須極薄、必須同時有 32/64 位元（現在還有 ARM64）版本，而且一旦改動就得重新註冊。PIME 的做法是把「怎麼組字」全部推到另一個行程，DLL 只做三件事：收按鍵、送 JSON、把回覆套用到組字視窗。

3內建後端：Python、Node、Go
2段 IPC：named pipe、stdin/stdout
15 s後端無回應的 watchdog 上限
3 種架構x86、x64、ARM64X（含原生 ARM64）
為什麼需要 launcher

DLL 活在別人的行程裡，不能自己管理後端的生死。於是有一個常駐的 PIMELauncher.exe：它建立 named pipe 等待 DLL 連線、按需啟動後端、監控 stdout、卡住就殺掉重啟。DLL 完全不知道後端是 Python 還是 Go。

02架構

四種角色，兩段通道。箭頭兩端都是 JSON，一行一個物件。

TSF → launcher：純 JSON，一行一個。launcher → backend：<client_id>|<JSON>。backend → launcher：PIME_MSG|<client_id>|<JSON>。

C++ / TSF

PIMETextService

唯一被 Windows 載入宿主行程的部分。收按鍵、維護組字狀態、透過 pipe 發請求；回覆的 seqNum 不對就關線重設。必須跟宿主 app 同架構。

C++ / static lib

libIME2

TSF 的封裝層（submodule，EasyIME/libIME2），把 COM/TSF 的樣板工作收起來，與 PIME 本身無關，可以單獨拿去寫別的輸入法。

Rust / x86

PIMELauncher

pipe server + 路由 + 行程管理。依 backends.json 啟動後端，用 (client_id, seqNum) 記 pending，15 秒沒回就殺掉重啟。

Python / Node / Go

Backends

真正的輸入法邏輯：ime.json 宣告 GUID 與模組，服務實作 textReducer（處理按鍵）與 response（產生回覆）。

NSIS

installer

註冊 TSF、寫 registry、依架構放置 DLL。Windows 11 ARM64 改註冊 ARM64X forwarder，讓原生與模擬的 x64 行程共用同一個 CLSID。

設定

backends.json + ime.json

backends.json 決定哪個語言設定用哪個後端；每個輸入法目錄的 ime.json 提供 GUID、顯示名稱與模組入口。

03一個按鍵的旅程

以「在記事本打一個注音」為例。第一次連線會多一段 init，之後每個按鍵都是同一個循環。

  1. TSF 呼叫 DLL

    使用者的按鍵先經過 Windows TSF，落到 PIMETextService 的 key handler。此時還沒有任何跨行程通訊。

  2. 建立連線與 init

    pipe 還沒開就建一條，並送出 init：內容是目前語言設定的 GUID。這是每條連線的第一個請求，後端靠它決定要載入哪個輸入法。

  3. launcher 解析 GUID

    backends.json 說這個語言設定屬於哪個後端；後端還沒跑就啟動它（工作目錄、命令、參數都寫在設定裡）。之後 launcher 給這條連線一個新的 UUID。

  4. 轉發

    launcher 把請求改寫成 <uuid>|<JSON> 寫進後端的 stdin。同一後端的所有使用者共用這條 stdin，靠 UUID 區分。

  5. 後端處理

    後端找到對應的 service，呼叫 textReducer 更新狀態、產生組字結果，再以 PIME_MSG|<uuid>|<JSON> 寫到 stdout。

  6. 路由回 DLL

    launcher 依 UUID 找到連線、把 payload 送去；同時用回覆裡的 seqNum 清掉 pending 記錄（只用來判斷後端有沒有卡住，不用來驗證內容）。

  7. DLL 驗證 seqNum

    DLL 比對回覆的 seqNum 與自己送出的號碼。相符才把組字結果套用到畫面上；這是最後一道防線。

  8. 失敗就重設

    seqNum 不符、JSON 壞掉或逾時：回應設為 null、關閉 pipe、清掉語言列按鈕。下一次按鍵會重新連線、重新 init。

時間常數

一般按鍵的 RPC 逾時是 2 秒；init 與 onActivate 是 15 秒（冷啟動要載入字典）。launcher 的 watchdog 也是 15 秒，但它量的是「請求送出後多久沒回覆」，而且是一秒掃一次。兩邊的 15 秒不是同一個 deadline。

04訊息格式

全部是 UTF-8 JSON，一行一個物件。差別只在誰加前綴。

區段格式範例
TSF → launcher 純 JSON，換行結尾 {"method":"filterKeyDown","seqNum":7,"charCode":65}
launcher → backend <client_id>|<JSON> 3f2a…|{"method":"filterKeyDown","seqNum":7}
backend → launcher PIME_MSG|<client_id>|<JSON> PIME_MSG|3f2a…|{"success":true,"seqNum":7}

seqNum 的責任分工

seqNum 由 C++ 客戶端產生（每條連線遞增），後端必須原樣回傳。launcher 只把它當 pending 記錄的鍵：送出時插入、回覆時刪除、15 秒沒刪就殺後端。真正「號碼不對就拒絕」的判斷在 DLL 裡；因此一個亂回 seqNum 的後端會先讓 DLL 關線重設，launcher 端則可能留下過期記錄直到 watchdog 出手。

設計含意

launcher 是路由器，不是驗證器。它不知道每個 method 的語意，也不該知道；只要 UUID 對得上就把 bytes 送過去。這個分工讓新增 method 不必改 Rust，代價是錯誤只能由兩端各自處理。

05三個後端

同樣的協定，三種行程模型。選一個讀就好，其他兩個的差異都在「狀態放哪裡」。

最完整的參考實作。每個 client 一個 Client 物件，保存 service 與組字狀態；service 由 serviceManager 依 ime.json 動態載入。close 會回 {"success":true,"seqNum":n}；單行處理外層包了 try，壞掉的請求不會帶走整個行程。

python/
├── server.py          # 讀 stdin 逐行、分派、寫 stdout
├── serviceManager.py  # 掃描輸入法目錄、載入模組
├── textService.py     # service 基底類別
└── input_methods/     # 每個輸入法一個目錄 + ime.json

用 vendored 的 nime（放在 node/node_modules，隨 repo 追蹤）管理連線與 method 分派；server.js 只提供「GUID → service」的解析函式。service 只需實作 textReducer 與 response。這一層的歷史問題最多：未知 GUID 或沒先 init 的請求會讓 nime 對 null 解引用，整個行程死掉——這正是 #936／#937 的來源。

node/
├── server.js          # createServer(resolveService) + listen
├── loadServices.js    # 讀 input_methods/*/ime.json
├── input_methods/     # meow、emojime、McBopomofo…
└── test/              # server.test.js（stdin/stdout 黑箱測試）

單一 server.exe，自己維護 clients map 與 JSON 編解碼。init 失敗、未知 method、未初始化 client 都會明確回 success:false；錯誤處理比其他兩個後端完整，但功能與輸入法數量較少。

go-backend/
├── server.go          # stdin 迴圈、init、method 分派、sendResponse
└── pime/              # 舊版另一個 server 實作（不在 backends.json）

共同契約

行為規則
每行一個 JSON不接受多行物件；stdout 只能有協定行或無害的除錯輸出（沒有 PIME_MSG| 前綴會被丟棄）。
每個請求一個回覆即使失敗也要回，且要帶回同一個 seqNum；不回覆會讓 launcher 的 pending 記錄過期。
close 要回覆launcher 在 client 斷線時送 {"method":"close"}，並期待回覆來清 pending。
狀態屬於 client同一後端服務多個使用者，組字狀態不能放在全域。

06建置與測試

這個 repo 有一半只能在 Windows 上驗證；先分清哪些事情在哪裡做。

工作在哪裡跑指令
TSF DLL（x86 / x64 / ARM64）Windows + CMake/MSVCbuild.bat
Launcher 與其測試Windows（cargo test）cd PIMELauncher && cargo test
Node 後端測試任何有 Node 的機器cd node && npm test
Python 後端測試任何有 Python 的機器python -m unittest discover -s tests -p "test_*.py"
安裝檔Windows + NSISmakensis installer/installer.nsi

CI（.github/workflows/ci.yaml）在 windows-2025 上把這串全部跑一次：Rust 測試、Python/Node 測試、三種架構的 DLL、NSIS 安裝檔，最後交給 SignPath 簽章。也就是說，Rust 與 C++ 的編譯錯誤只有推上去才會知道；本機（Linux）能跑的是 Node 測試、部分 Python 測試與讀碼。

除錯開關

PIMELauncher.exe /console 開主控台看即時日誌；/log-file <path> 寫檔；/quit 結束常駐實例。正常背景模式只記 WARN 以上，避免日誌 I/O 影響輸入延遲。

09名詞

照 GLOSSARY.md 的定義；混用這些詞是讀這個 repo 最常見的卡點。

Service
由後端承載的輸入法模組，以語言設定 GUID 註冊，實作 textReducer 與 response。不要叫它 text service。
Backend
承載 service、說 line protocol 的行程（python、node、go-backend），名字寫在 backends.json。
PIMETextService
C++ TSF 客戶端 DLL，唯一被 Windows 載入宿主行程的部分。
Client
一條 pipe 連線，用新產生的 UUID 識別；不是 session，也不是使用者。
Init
每條連線的第一個請求，帶語言設定 GUID，決定後端與 service。
Watchdog
launcher 每秒掃 pending 表；任何一筆超過 15 秒沒被回覆清掉，就殺掉整個後端並在 1 秒後重啟。
