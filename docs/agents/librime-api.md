# Rime backend: the bundled `rime.dll` is the authority

Any claim about what a `Rime*` call returns is settled by probing the committed
`python/input_methods/rime/rime.dll` through the ctypes bindings, or by the
declared signatures in the `RimeApi._fields_` list of
`python/input_methods/rime/librime.py`. The librime source tree is **not**
vendored in this checkout (only the schema collection
`python/input_methods/rime/brise` is a submodule), so nothing is carried over by
analogy from the libchewing conventions in `docs/agents/chewing-api.md`: the two
libraries differ, and each was probed on its own.

## Re-deriving a convention

Two ways, both cheap and both offline:

```sh
# the declared signature of any API member, straight from the binding
grep -n '"config_get_bool"' python/input_methods/rime/librime.py
# replay the measurements with the bundled interpreter
python/python3/python.exe -m unittest discover -s tests -p "test_rime_app_options.py" -v
```

The bindings resolve every member of the `RimeApi` struct by name; an entry
absent from `_fields_` is not callable through `rime`, and no member is
normalized on the way back — the C `Bool` arrives as an `int`.

## Measured return conventions (bundled `rime.dll`, 2026-11-08)

| Call | Success | Failure / "not found" |
| --- | --- | --- |
| `RimeConfigOpen(name, &cfg)` | `1` for a profile found in the user dir, else the shared dir | `0` (no such profile) |
| `RimeConfigInit` / `RimeConfigLoadString` | `1`, usable standalone config | `0` |
| `RimeConfigGetBool(cfg, path, &v)` | `1`, `v` = `0`/`1` for a **bool node only** | `0` — an int node, a missing path and an unknown key are indistinguishable |
| `RimeConfigGetInt(cfg, path, &v)` | `1`, `v` = the int | `0` (a bool node is not found here either) |
| `RimeConfigGetCString(cfg, path)` | the text: `true`/`false` for a bool, digits for an int | `None` |
| `RimeConfigBeginList(it, cfg, path)` | `1` for a **sequence** (`menu`) | `0` for a **map** (`style`, `app_options`) — read maps by full path instead |
| `RimeGetOption(session, name)` | `1` when the option is on | `0` for a false option **and** for an unknown option |
| `RimeSetOption(session, name, value)` | no return value, `RimeGetOption` reflects it | — |
| `RimeCreateSession()` | non-null pointer after setup + initialize | null |

Three further facts the probes fixed:

* **Path matching is case-sensitive**: `app_options/python.exe/ascii_mode` is
  found, `app_options/PYTHON.EXE/ascii_mode` is not. The profile keys are
  therefore compared exactly as written — see `rimeAppOptionNames` in
  `python/input_methods/rime/librime.py`.
* **The engine does not apply `app_options` to the session options itself**: a
  fresh session reports `ascii_mode` `0` even when the profile carries
  `app_options/python.exe/ascii_mode: true`. The pass-through is the Python
  layer's job, in `rimeApplyAppOptions`.
* **One `RimeSetup` per process**: the second call aborts with glog's
  `Could not create logging file: Invalid argument` and
  `*** Check failure stack trace: ***`. A bare `RimeInitialize(NULL)` after
  `RimeFinalize` is fine, which is why `rimeInit` guards setup plus the first
  maintenance run behind `_rime_started`. The engine calls around the deploy
  command are the module's own, as of `upstream/master` `97f7efa`:
  `rime.finalize` is registered once with `atexit.register` at import, so
  `ID_DEPLOY` runs `deploy_config_file` after the maintenance pass with no
  `finalize()` / `initialize(None)` pair, and `onKeyboardStatusChanged` calls
  `createSession()` only while `session_id` is still `None`.

## Where the engine writes

`RimeSetup` takes both directories from the traits that `rimeInit` builds; the
log files land in the log directory that the tray menu opens
(`%TEMP%` on Windows, the same value `ID_LOG_DIR` reports in
`python/input_methods/rime/rime_ime.py`) as one glog triple per start, named
`Rime.<app>.<host>.<user>.log.{INFO,WARNING,ERROR}.<stamp>.<pid>`.
`RimeGetSyncDir` returns `<user dir>/sync`. Both directories are bounded by the
retention pass documented in `python/input_methods/rime/librime.py`; the
profile keys that layer reads are listed in its module docstring, and the
shipped example lives in `python/input_methods/rime/data/PIME.yaml`.
